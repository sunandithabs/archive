Automotive OTA & Boot Security

BOLTBoot & OTA Lockdown Toolkit

Automotive Security Firmware Integrity 2026 GitHub ↗

Overview

BOLT is a signed OTA update and boot integrity framework for automotive ECUs, built entirely in software. A signing pipeline produces firmware images backed by a real X.509 chain, a bootloader verifies and flashes them onto an A/B partition layout, and an attacker toolkit throws four different attacks at the whole thing to see what actually holds.

Root CA signs an OEM cert. OEM cert signs images, manifests, and OTA metadata. The verifier checks the full chain before it trusts anything, and a Rich dashboard renders what happened when the attacks run.

Named half after what it does and half after watching Max put down a qualifying lap in the RB. Same idea either way: verified, locked down, and quick about it.

Motivation

Automotive OTA has a track record of shipping without the basics: no rollback protection, no channel integrity separate from image signing, no A/B fallback when a flash gets interrupted halfway. The 2015 Jeep Cherokee remote exploit happened partly because the head unit accepted an old, vulnerable firmware image with nothing stopping the downgrade.

BOLT builds each of these failure modes as a real, working attack and pairs it against the mitigation that's supposed to stop it. Not a paper description of rollback protection, an actual rollback index check that a real downgrade attempt actually fails against.

Trust Chain

Root CA (offline, long-lived) | | signs v OEM signing cert (short-lived, rotatable) | | signs v Firmware image + manifest + OTA metadata | | verified by v Verifier.from_cert_chain() -- issuer match, signature, validity window

A compromised OEM key gets rotated by issuing a new cert off the root, no re-provisioning needed on every ECU in the field. The root key itself is assumed offline and HSM-protected in any real deployment. BOLT's pki.py generates a full chain locally for simulation, and none of that key material should ever be treated as production-grade.

Image Format & Signing

Each image is a 4-byte header length, a JSON header holding version, rollback index, and signature, then the payload. The signature itself is RSA-PSS over SHA-256, computed across version, rollback index, and payload together, so none of the three can be swapped independently without invalidating it.

pipeline/manifest.py signs a separate manifest per ECU listing target firmware names, lengths, and SHA-256 hashes. That's metadata about what should be installed, kept independent of the image bytes. pipeline/ota_metadata.py goes further, splitting update authority into a director role that assigns targets to ECUs and an image repository role that attests to what targets actually exist, loosely modeled on Uptane's role separation. A compromised director alone can't push a malicious update unless the target it names also shows up in the separately signed image repository.

A/B Partitioning

Every flash writes to the inactive slot. Rollback commit and slot activation happen only after signature and rollback checks pass, so a crash or truncated write mid-flash never touches the currently active, known-good image. It's the same approach Android and most automotive OTA systems use for exactly this reason.

bootloader/flash.py and bootloader/flash_ecu.py model this against a single byte-addressed virtual flash file with named regions: bootloader, slot_a, slot_b, rollback_counter, slot_state, manifest. Closer to how flash-backed ECUs actually lay out memory than a handful of separate JSON files would be.

Attack Suite

Four attacks run against a fresh signer/verifier pair each time. Downgrade replay flashes an older signed image, the same class of bug that let the Jeep Cherokee exploit through. Signature strip zeroes out the signature and tries to flash anyway. MITM tampers with an image in transit. Power loss simulates a truncated write mid-flash.

Each attack either gets blocked or it doesn't, and the event log records which, along with a one-line detail on what the attack actually did. run_attack_suite.py runs all four back to back and hands the results to a Rich terminal dashboard.

Running It

Setup is pip install -e ".[dev]", then generate keys and sign an image through pipeline.cli, or just run python run_attack_suite.py directly for the full four-attack pass against a throwaway signer and verifier. Tests cover the pipeline, bootloader, attacks, and detector modules through pytest, with ruff and mypy on top for lint and typing.

Verdict

Conclusion

All four attacks get blocked, and the threat model doc explains why each one maps to a real vulnerability class rather than a made-up one. The rollback index stops downgrade replay, the signature check stops a stripped image from flashing, the A/B layout stops a truncated write from bricking anything, and image-level signing stops MITM tampering regardless of what the channel itself does.

What's out of scope matters too: no revocation checking on OEM certs, no modeling of verifier-level compromise, no defense against a supply-chain attack that happens before the signer ever sees the payload. Those are real gaps, not oversights BOLT is pretending don't exist.

As a working demonstration of how the standard automotive OTA mitigations actually hold up against the attacks they're meant to stop, BOLT does the job.
