WatchtowerHoneypot-Based Threat Observation Platform

Honeypot Engineering 2026

Overview

Watchtower began as a simple SSH honeypot experiment and gradually evolved into a broader threat observation platform. Instead of exposing a single fake service, the project simulates a small corporate environment designed to attract interaction, capture attacker behavior, and provide visibility into how suspicious users move through a system.

The platform combines a public-facing company website, a fake employee portal, credential capture mechanisms, event classification logic, and a monitoring dashboard into a single environment. The goal was not to stop attacks, but to study them. Unlike traditional detection systems that rely on predefined signatures, Watchtower focuses on observation — every interaction becomes telemetry.

Most students encounter cybersecurity through isolated lab exercises, CTFs, or synthetic datasets. Real-world attacks are messy — attackers probe unexpected endpoints, reuse strange credentials, automate reconnaissance, and generate patterns that rarely appear in textbook examples. The goal was a controlled environment to observe this behavior directly while maintaining complete visibility into every action: can a realistic-looking environment be built that attracts interaction, records activity, and presents the resulting telemetry in a useful way?

Public corporate website. A fake organization, Nova Industries, with Home, About, Products, Careers, and Contact pages, existing primarily to provide legitimacy and encourage interaction.

Employee portal honeypot. A dedicated employee login portal acting as the primary honeypot surface. All login attempts are recorded regardless of success — usernames, passwords, source addresses, and user agents are captured and stored. Obvious attacker patterns (admin, root, sql, inject, shell, hack) are identified and treated differently from normal-looking activity. Rather than granting real access, the system redirects users into a simulated employee environment.

Decoy internal resources. The employee environment contains intentionally fake functionality — file upload/download endpoints and internal portal navigation — that never exposes real data but generates additional telemetry about what the visitor attempted to access.

Event collection pipeline. Every interaction is recorded inside an SQLite-backed event store, capturing timestamp, source IP, username, submitted payload, and user agent — turning ordinary web requests into a structured dataset suitable for analysis.

Threat classification layer. A lightweight classification engine assigns severity and a threat score based on suspicious keywords, SQL-like payloads, script injection attempts, repeated usernames, aggressive source activity, and high-frequency event bursts. Events are categorized low/medium/high severity with a 0–100 score. The objective was rapid prioritization of interesting activity, not perfect detection accuracy.

Monitoring dashboard. Exposes event streams, threat scores, unique source counts, high-risk activity summaries, and recent attacker behavior for near real-time review.

A major challenge during development was the lack of real traffic. A separate attack simulation framework was built to generate login attempts, portal visits, contact form submissions, career applications, file access attempts, and scanner-like behavior — sourced from multiple simulated IP pools (cloud providers, VPN endpoints, residential networks, IoT-style address ranges). The simulator creates hundreds of events per run, allowing the dashboard, scoring logic, and storage pipeline to be tested under realistic workloads.

The most important lesson was that telemetry is often more valuable than prevention. Building a system that captures behavior forces different design decisions than building a system that blocks behavior — more time went into what should be recorded, how activity should be classified, which events deserve attention, and how to distinguish noise from signal than into traditional access control.
