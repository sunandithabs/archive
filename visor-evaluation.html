Firmware Analysis

Visor BootManagerEvaluation

Firmware Analysis 2025

Overview

Visor is a graphical EFI boot manager. It presents a clean icon-based interface at boot rather than the text menu GRUB shows by default. This was an evaluation of whether it was worth adding to an existing Arch Linux and Windows 11 dual-boot setup, and whether it could eventually replace GRUB as the primary boot interface.

The answer was no, at least for now. But the process of getting there was the interesting part.

Motivation

GRUB works. It is also ugly. The default text menu is functional but not something you want to look at every morning. Visor promised a modern graphical alternative with a lightweight EFI-native implementation. Worth testing.

The constraint was safety: any test had to leave GRUB fully intact and recoverable. Replacing the primary bootloader on a daily-driver system without a fallback is how you end up with a paperweight.

Environment Assessment

Before touching anything, the current boot state was audited using bootctl and efibootmgr. The system was running in UEFI mode with Secure Boot disabled. GRUB was the active bootloader. The EFI System Partition contained GRUB's EFI loader, the Windows Boot Manager, and the standard UEFI fallback entries.

EFI boot entries were exported as a backup. The existing GRUB installation was left completely untouched throughout the entire evaluation. Any Visor test that required modifying GRUB files was ruled out before starting.

Build & Installation

The first build attempt failed immediately. Visor requires GNU EFI headers to compile and they were not present on the system. Installed gnu-efi, recompiled, and got a valid EFI executable: visor_x64.efi.

Visor was installed into a dedicated directory on the ESP: EFI/visor/. Nothing in the existing GRUB or Windows directories was modified. A new UEFI boot entry was registered for Visor using efibootmgr, sitting alongside the existing entries without displacing any of them.

Testing Strategy

Rather than changing the permanent boot order to test Visor, BootNext was used to trigger a one-time boot into Visor for a single restart. The default boot order stayed pointing at GRUB. If Visor failed completely, the next boot would go back to GRUB automatically. No intervention required.

This is the right way to test an unfamiliar bootloader on a machine you depend on. It costs one extra command and eliminates a whole class of recovery scenarios.

Results

Visor launched. The graphical interface loaded. The Windows Boot Manager entry was detected and displayed correctly. Selecting it booted Windows without issues. GRUB and the Arch Linux configuration were untouched after the test completed.

Arch Linux did not appear in the Visor menu. Visor's detection relies on Unified Kernel Images or EFI stub kernels sitting on the ESP, and the existing Arch setup uses a traditional GRUB-based workflow where the kernel lives outside the EFI partition. Visor has no way to find it automatically.

Getting Arch to appear would require generating a UKI and placing it on the ESP, a nontrivial workflow change for the existing setup.

The interface rendered at firmware resolution, which was noticeably lower than the display's native resolution. Not a dealbreaker, but worth noting.

Verdict

Conclusion

Visor is an interesting project. The implementation is clean, the installation is non-destructive, and the Windows detection works correctly out of the box. For a UKI-based workflow it would probably be a good fit.

For this setup, it is not ready to replace GRUB. The Arch Linux integration requires additional configuration that the existing workflow does not support without meaningful restructuring. That is not a flaw in Visor. It supports a specific set of boot mechanisms, and the current setup uses a different one.

GRUB stays. Visor goes on the list of things to revisit if the boot workflow ever moves toward UKIs.

Lessons Learned

The BootNext approach should be the default for any bootloader evaluation. It decouples testing from commitment. The boot order stays intact, the test runs once, and everything resets automatically. There is no good reason to permanently change boot order during an initial test.

Missing build dependencies are worth checking before assuming a project is broken. The gnu-efi issue would have looked like a project defect without reading the build output carefully. It was just a missing package.

Graphical bootloaders that work at the EFI level are constrained by what the firmware hands them. Resolution, input handling, and asset loading all happen before the OS is involved. That limits what they can do, but it also means they are extremely lightweight. Visor loads and exits in seconds. GRUB does not.
