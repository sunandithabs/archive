SimulynDocker Deployment

A containerized deployment that fought back at every networking layer before coming up clean.

Overview

Simulyn is a virtual engineering laboratory platform meant to run as a containerized service, with a login flow, a student dashboard, and a coding workspace served from inside Docker. Getting it running on an Arch Linux host should have been the boring part of the project. It was not. The deployment surfaced a chain of networking failures that had nothing to do with the application itself, and clearing that chain became the actual work.

Setup

Docker was not present on the host. Package mirrors were refreshed, Docker and Docker Compose were installed, and the daemon was enabled and started through systemd. User permissions were adjusted so the daemon socket could be reached without elevated privileges on every command. Before moving further, the daemon's running state was checked directly rather than assumed, since a service that enables cleanly does not always mean it started cleanly.

Investigation Flow

The path from a fresh install to a working container did not move in a straight line. It moved through a sequence of suspects, most of which were eliminated rather than confirmed.

Networking Failure Chain

Image pulls failed immediately, and the first instinct was to treat it as a single problem. It was not. The first symptom was repeated TLS handshake timeouts during image downloads, which pointed toward Docker Hub connectivity rather than anything local. Reachability was tested directly with curl against Docker Hub to confirm the network path itself was the suspect, not a certificate or proxy issue on the host.

That led to an IPv6 routing fault: certain image layers stalled mid-transfer in a pattern consistent with the daemon attempting IPv6 first and failing silently before falling back. Disabling the problematic IPv6 behavior cleared that stall.

DNS resolution inside the daemon needed explicit configuration once routing was no longer the variable. The default resolver behavior had been masking a separate misconfiguration the whole time.

Socket permission errors surfaced last, traced to group membership not having been correctly applied for the active session.

Each of these was verified in isolation before being marked resolved. The daemon's overall health was confirmed with the standard hello-world image only once DNS, routing, and socket access were all working at the same time, not just individually.

Container Build & Verification

With the networking layer cleared, the Simulyn image built successfully from the project's own Dockerfile. Docker Compose handled both image creation and container startup in a single pass. Port mapping between host and container was checked explicitly rather than assumed to be correct, and the application became reachable on localhost:3000 shortly after.

Validation Checkpoints

Once the container was running, a short set of checks confirmed it was actually serving the application rather than just exposing an open port. The demo account autofill and role-based login redirect were tested and behaved as expected, and the core frontend files, including the login page, the student dashboard, and their supporting scripts, were confirmed to load correctly through the browser. Both checks passed without further intervention.

Forward Work

The debugging process surfaced a couple of interface gaps worth noting for later: the dashboard lacks visual hierarchy and the coding workspace has no data structure visualizations. No further scope was defined beyond that observation.

Key Takeaway

This investigation was never really about Simulyn. The application built and ran without incident once it had a working network path to pull from, which means the actual engineering problem was four stacked failures in the host's networking stack: a TLS layer that looked broken but wasn't the root cause, an IPv6 path that failed quietly instead of loudly, a DNS resolver hiding behind both of them, and a socket permission gap that only became visible once everything above it was already fixed.

What mattered was the order of elimination. Fixing TLS first did not fix the deployment, and neither did fixing DNS in isolation. Progress only happened once each layer was tested independently and ruled in or out before moving to the next, rather than assuming the first plausible cause was the real one.

The result is a deployment that now starts cleanly and a clearer mental model of how this host's networking stack behaves under Docker, which is the part of this work likely to be reused the next time something fails to pull an image for no obvious reason.
