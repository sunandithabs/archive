WARDENUDS SecurityAccess Attack & Detection

Automotive Security Detection Engineering 2026 GitHub ↗

WARDEN is a small SocketCAN testbed built around ISO 14229, the UDS (Unified Diagnostic Services) spec that governs how diagnostic tools talk to an ECU. It simulates a diagnostic session on a virtual CAN bus, attacks the SecurityAccess seed-key exchange with a brute-force client, and runs a detector alongside that watches the same bus and flags the attack while it's happening.

Three pieces, one bus. The server plays a weak, deliberately breakable ECU. The attacker just grinds keys. The detector is the one actually paying attention.

UDS SecurityAccess is the gate that separates "read some sensor values" from "flash the ECU" or "unlock a restricted diagnostic session." A lot of the interesting automotive CVEs over the past few years trace back to weak or predictable seed-key algorithms: XOR masks, fixed offsets, algorithms an attacker can reverse from a handful of seed-key pairs sniffed off the bus. That's a detection engineering problem as much as a crypto one: the algorithm being weak matters less if someone is watching for the brute-force pattern that exploiting it produces.

The point wasn't a novel key-recovery technique. It was getting the whole loop working on real UDS session and service semantics, vulnerable server plus exploit plus detector, so the detection logic has to handle actual protocol structure instead of some toy stand-in.

Request ID 0x7E0 (tester → ECU) Response ID 0x7E8 (ECU → tester) attacker/client ──▶ 0x7E0 ──▶ server (ECU sim) server (ECU sim) ──▶ 0x7E8 ──▶ attacker/client │ └──▶ detector (passive, sniffs both IDs)

Standard 11-bit physical addressing pair, matching how most OEM tools address a single ECU on a bus. The detector doesn't participate in the session at all. It just listens on both arbitration IDs and reconstructs what's happening from the request/response pairs, which is the same constraint a real bus-tap IDS would have.

The server implements two services: DiagnosticSessionControl (0x10), for switching between default and extended sessions, and SecurityAccess (0x27), for the seed-key handshake. Request a seed, get a random 16-bit value back. Send a key back, and the server checks it against seed XOR 0x5A5A.

An XOR mask with a fixed key is about as weak as a seed-key scheme gets. Recover one seed-key pair and you have the mask, permanently. That's intentional. The point of the simulator isn't to be a realistic crypto challenge, it's to reproduce the shape of a class of real weak implementations closely enough that the resulting bus traffic is representative.

There's also a lockout: three failed key attempts and the server stops issuing seeds for ten seconds, responding with NRC 0x36 (exceeded number of attempts) instead. This matters for the detector, because it means a naive brute-force script generates a very specific traffic signature, bursts of seed requests and negative responses separated by lockout gaps, rather than a smooth stream of guesses.

The attack client opens an extended diagnostic session, then loops: request seed, guess a key, check the response, repeat. It has no idea the mask is XOR. It's just trying sequential integers, which is a deliberately unsophisticated attacker model. A real key-recovery attack against a static XOR mask wouldn't brute-force at all; it would recover the mask from one exchange and use it forever. Brute-forcing here stands in for a whole class of attacker behavior against schemes that aren't quite XOR-simple: iterative guessing against a bounded keyspace, timing side channels, or automated fuzzing against a session that doesn't validate strongly enough.

The interesting part is what the lockout does to the attack. Once the server locks, request_seed() returns None, and the attack script gives up rather than looping forever against a wall. That's realistic. Most brute-force tooling backs off or dies on a hard lockout response instead of hammering blindly.

The detector runs two sliding-window counters over the same traffic. One counts SecurityAccess "send key" requests (0x27 0x02 on the request ID); the other counts negative responses to SecurityAccess (0x7F 0x27 on the response ID). Both use a 15-second window with a threshold of 3.

Three-or-more key attempts in the window raises a WARNING. Three-or-more failures in the window raises a CRITICAL: "probable SecurityAccess brute-force." The distinction matters: a legitimate technician fat-fingering a key twice shouldn't page anyone, but a run of consecutive negative responses in a tight window is a much stronger signal, and the severity split reflects that.

Structurally it's just a deque-based sliding window: append a timestamp, prune anything older than the window, check length against the threshold. No ML, no baseline modeling. Just a well-chosen window and threshold matched to an attack pattern that's already well understood. Most of the real detection engineering work was in picking what counts as an event and finding a window that catches a brute-force run without also flagging normal diagnostic chatter.

The full loop needs a vcan interface (modprobe vcan, add and bring up vcan0) and three processes: server, detector, then the attack script pointed at however many attempts you want to throw at it. There's also a demo.py that runs all three in-process over a virtual bus, for when setting up a real vcan interface isn't worth it just to see the detector fire.

Watching it live is the whole point. The attack script grinds through key guesses, the server rejects them and eventually locks out, and the detector's log fills with WARNING lines that escalate to a CRITICAL the moment three negative responses land inside the window, usually well before the lockout itself would have stopped anything.

Conclusion

WARDEN does what it set out to do: give a concrete, protocol-accurate example of why SecurityAccess brute-forcing is detectable even when the underlying algorithm is broken. The weak XOR mask is the vulnerability; the sliding-window detector on negative responses is the mitigation that doesn't depend on fixing the crypto.

It's a simulator, and it shows: there's no CAN bus load noise here, no multi-ECU traffic to filter, nothing resembling a legitimate high-frequency diagnostic tool that might trip the threshold. The obvious next step is layering in benign traffic, normal diagnostic sessions, routine reads, to see whether the window still holds once the bus isn't just attacker and ECU talking to each other.

As a self-contained piece of detection engineering against a real UDS service, though, it does hold together.
