Volume Restructuring& Firmware Security

Firmware Analysis 2026
Jump to Key Findings

Two investigations. One involved a Linux partition that should have been easy to expand and wasn't. The other involved an old Android device with a locked bootloader and a boot trust chain that needed to be understood before anything could be flashed.

They ended up in the same page because they share the same basic shape: both required getting underneath the operating system and reasoning about structure that's normally invisible. The disk investigation worked at the sector level. The Android investigation worked at the firmware level. Neither could be solved from the OS layer down.

The starting situation: a dual-boot drive with an ext4 Linux partition and an NTFS Windows volume sitting on the same disk. The goal was to expand the Linux partition. There was unallocated space. This should have taken five minutes.

Every partition tool tried either refused outright or claimed the operation was impossible. GParted bailed. The Windows disk manager wouldn't touch it. Nothing would move the NTFS boundary left to free up the space adjacent to the Linux partition.

The reason, once actually looked at, was NTFS metadata placement. NTFS doesn't just store file data where it fits. It places structural metadata at specific sectors across the volume, notably $MFT mirror copies, which are backup copies of the Master File Table written at fixed offsets into the partition. Standard tools refuse to move these because if you relocate them incorrectly, the NTFS volume is silently corrupted. The failure mode is not "error message." The failure mode is data loss you don't notice until it's too late. So every tool just says no.

The approach was to stop using tools that couldn't reason about the problem and start working at the sector level directly. First, map the partition table using GPT geometry to understand the actual sector layout. Second, identify exactly which sectors held the immovable metadata blocks and what they were. Third, determine whether the required boundary movement would actually touch those sectors, and if so, how to neutralize the constraint safely before adjusting anything.

The metadata blocks were identified, handled correctly, and the GPT geometry was reconstructed to reflect the new partition boundaries. The Linux partition expanded by around 60% on a live system with no data loss.

The Lego Batman game ran fine. That was the point of this entire operation, and it was worth it.

The reason standard tools refuse this operation is sound. If you do not know exactly which sectors you are moving and what happens if the move is wrong, you should not attempt it. The tools are not being overcautious. They are protecting you from a failure mode that looks like success right up until it isn't. Working at the sector level requires being certain, not confident.

A MediaTek device with Android Verified Boot enabled, a locked bootloader, and an outdated Android version that vendor support had abandoned. The goal was to flash a custom Generic System Image to get a usable OS on the device.

The naive approach: find the unlock command, run it, flash the image. That did not work here. This device had a layered verification chain where each stage checks the cryptographic signature of the next before handing off control. You cannot simply bypass the last stage. You have to understand the whole chain first.

The chain on a MediaTek device looks like this:

BROM → Preloader → LK (Little Kernel) → Kernel → Android

BROM is the Boot ROM burned into the chip at manufacture. It is read-only and cannot be modified. It loads and verifies the Preloader. The Preloader loads and verifies the Little Kernel. The LK loads and verifies the kernel. Android Verified Boot then sits on top of that, checking the system partition against a vbmeta image before allowing the OS to start. Every link in this chain has to hold or the device refuses to continue.

The approach was to map the full chain before touching anything. The actual intervention involved patching the vbmeta image that AVB checks against to disable verification flags, then using fastbootd rather than standard fastboot. The distinction matters: standard fastboot runs in the bootloader and has limited partition access. fastbootd is a userspace implementation with access to logical partitions that standard fastboot cannot reach. Flashing a GSI requires it.

Two additional problems appeared during the process, and both had to be diagnosed before the main operation could continue. The device kept dropping the diagnostic connection partway through the flash sequence, producing BROM-level handshake timing failures.

Separately, Preloader VCOM sync was unstable, causing the flash tool to lose the device mid-transfer. SP Flash Tool on Linux was the only tool with enough access to the preloader layer to actually see what was happening at the connection level.

The GSI was flashed. The device accepted it. Getting the OS fully functional after that is still unfinished work. Some things take longer than one session.

NTFS metadata placement is a real constraint, not a tool limitation. The tools that refuse partition boundary moves near $MFT mirrors are correct to refuse. Working around that requires sector-level awareness, not a better tool.

Android Verified Boot is a chain, not a lock. Trying to bypass any single stage without understanding what's upstream and downstream of it will fail. The BROM cannot be modified. Everything above it can be, but only if the full chain is understood first.

Connection stability at the preloader layer is a real debugging problem independent of firmware logic. A flash that keeps dropping the device is a transport problem, not a verification problem. They look similar from the outside and require different fixes.

fastbootd and standard fastboot are not interchangeable. Standard fastboot lives in the bootloader. fastbootd runs in recovery and has access to the logical partition layer. Knowing which one you need before starting saves time.

Both investigations required the same mental shift: solve the problem one layer below where it's visible, not at the layer where it's failing. And incomplete outcomes are still worth documenting: the Android work never finished, but the investigation produced real understanding of MediaTek boot chains, AVB structure, and what SP Flash Tool can see at the preloader layer independent of whether the OS came up.
