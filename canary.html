Overview

CAN was designed in the 1980s for a closed, trusted network. It has no authentication and no encryption. Any node on the bus can send a frame claiming to be any other node, and every other ECU will believe it. That assumption stopped being safe once cars gained Bluetooth, cellular modems, and USB ports. Miller and Valasek's 2015 Jeep Cherokee remote takeover is the proof of concept: CAN injection can reach steering, braking, and acceleration.

CANARY is an observability and intrusion detection platform built around that problem. It simulates a multi-ECU vehicle network with realistic timing and arbitration, watches that traffic the way a security analyst would, and flags the behaviors that indicate spoofing, replay, flooding, or malformed frames. It is not a CAN protocol implementation. The simulator's only job is producing traffic realistic enough for the detection engine to have something honest to watch.

The Detection Engine

A malicious CAN frame is very often a perfectly well-formed CAN frame. Catching an attack means watching behavior over time, not validating a single message in isolation. CANARY tracks a per-ID baseline, expected source, expected size, expected period, and runs every frame through six independent rules: unknown ID, source mismatch, malformed size, impossible frequency, sustained flooding, and replay of an identical payload outside its normal rhythm.

Every rule that fires produces a severity-tagged alert, from LOW to CRITICAL. A live terminal dashboard reports bus utilization, arbitration latency, top talkers, and recent alerts, built on the same telemetry the detector consumes, so the dashboard never needs to know anything about bus internals to draw an accurate picture.

One piece of the project lives in C rather than Python: the CRC-15 checksum every real CAN frame carries, computed one bit at a time via ctypes, matching how CAN controllers do it in hardware. It is the one place in the codebase where reaching for C is the honest engineering choice rather than a language flourish.

Verifying Against Real Linux SocketCAN

A simulation proves the detection logic works. It does not prove the system can talk to an actual Linux CAN interface. CANARY implements SocketCANBus against the kernel's native SocketCAN API using a raw AF_CAN socket, no external library, hand-packing the kernel's struct can_frame directly.

The chain that made this possible without touching the rest of the system:

BusInterface → SimulatedBus → SocketCANBus → vcan0

The detector, logger, and dashboard all depend on BusInterface, never on a concrete bus class. SocketCANBus dropped in as a second implementation with zero changes anywhere downstream, which is the actual payoff of designing the abstraction before there was a second consumer for it.

Testing it against a real vcan0 virtual interface surfaced an actual kernel-level bug on the first run: a sent frame produced zero received frames. SocketCAN does not loop a sent frame back to the socket that sent it by default, only to other sockets on the interface. Since offer() and the receive loop shared one socket, the fix was enabling CAN_RAW_RECV_OWN_MSGS explicitly. Real ECU-to-ECU traffic never hits this, since sender and receiver are different processes. It only surfaced because the test sent and listened on the same bus instance, which is exactly the kind of thing that only shows up once you test against the real kernel instead of trusting the code by inspection.

Key Findings

Modules built and unit-tested in isolation can still hide integration bugs. Every ECU, bus, logger, and detector module passed its own tests early. Two real bugs only appeared once the full simulator ran end to end: ECU frames were timestamped with the wall clock instead of simulated time, and the stats engine compared latency across two different clocks. Isolated tests proved each part correct on its own terms. Only running the whole system proved the terms agreed with each other.

Protocol completeness and detection engineering are different goals, and conflating them wastes effort. Bit-stuffing, ACK slots, error frames, remote frames, overload frames, and the bus-off state machine are all real parts of the CAN specification. None of them change what a behavioral detector can observe, so all of them were deliberately left unimplemented and documented as such, rather than built for the sake of matching the spec.

SocketCAN's own-message loopback behavior is a real, documented kernel quirk, not a framework limitation. It only surfaces when a single socket both sends and listens, which is unusual for real ECU traffic but exactly the shape a detection tool needs. Finding it required testing against vcan0, not reading the man page.

Lessons Learned

An interface extracted after four modules were already built cost nothing to retrofit, because every consumer had been talking to the bus through subscribe() and offer() from the first module onward. The lesson generalizes past this project: decoupling early is what makes a late architectural correction cheap instead of a rewrite.

A project's identity is decided by what it refuses to build, not only by what it builds. CANARY earns the label "detection engineering platform" specifically because features that would have made it a more complete CAN simulator, and a less focused security tool, were left out on purpose.

Simulation-only claims and kernel-verified claims are not the same sentence, even when the code is identical. The SocketCAN integration was written correctly before it was ever run against a real interface. It only became a true claim once it was actually tested against one, and the bug that surfaced in that first real run is the difference between the two.

ELI5 tldr
01 Think of a race track with several cars sharing one lane. CANARY is the team of stewards watching every car, not to see if any single car looks fine, but to notice when a car starts lapping impossibly fast, uses another car's number, or repeats an old radio message pretending it's live.
02 Before any of this could run on a real track instead of a practice simulator, it had to prove it could actually talk to real timing equipment. The first real test came back with zero results. Turned out the equipment doesn't echo your own signal back to you unless you ask it to. One setting fixed it.
03 The stewards were never taught every rule in the rulebook, only the ones that actually change what they can see from the stands. That was on purpose.
