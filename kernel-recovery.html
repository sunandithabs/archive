Kernel Reconstruction& Linux Recovery

System Recovery 2025

Two separate boot failures, a few months apart. Different root causes, same basic lesson: the thing that looks broken usually isn't the actual problem. This documents both incidents, what each one actually was, and how they got fixed.

The first happened during initial setup. The second dropped in after a routine package update, the kind you run without thinking. Both required getting past the visible symptom before any real debugging could start.

Problem

Fresh dual-boot setup using Ventoy. Installation worked. Then, during bootloader configuration afterward, something broke and Linux stopped booting entirely. On startup: a display manager crash. Hard stop, no desktop, no logs in view.

The obvious read was a graphics or display stack problem. That's what it looked like. It was not that.

Investigation

Booted from a live USB. Mounted the broken root partition, then used chroot to enter the non-booting system from inside the live environment. This is the move when you need to run commands against a broken install as if you were logged into it normally. From there, the actual error logs were accessible.

The display manager was crashing, yes. But it was crashing because it couldn't load. And it couldn't load because a proprietary GPU driver was conflicting at a lower level, corrupting the init sequence before the display stack even had a chance to start. The display manager was just the first visible casualty.

The wrong assumption: display manager broken, fix the display manager. The right read: something upstream of the display manager is poisoning the boot. Finding that required getting inside the system and actually reading what was failing and why.

Resolution

Rebuilt initramfs from inside the chroot to regenerate the early userspace without the conflicting driver state. Regenerated vmlinuz. Repaired the EFI System Partition entries, then rebuilt GRUB from scratch to make sure the bootloader was pointing at a clean kernel image. System came back up clean on next boot.

Problem

A few months later. Ran a package update before going to sleep, which is a fine idea until it isn't. Next morning: instead of a desktop, a BusyBox shell. No display. No cursor. No wifi. Just a minimal emergency shell sitting there.

The error logs pointed at an I/O failure. Which suggested storage corruption, maybe a bad write during the update. That's the obvious read. It was also wrong.

Investigation

The I/O failure wasn't random corruption. The SSD was becoming intermittently invisible during boot, which made everything downstream look like a read error. The real cause was a VMD/Intel RST kernel incompatibility: the storage controller driver was loading in the wrong sequence during init, meaning the kernel was trying to access the drive before the controller responsible for it had finished initializing.

This one was harder to find because the error output was genuinely misleading. An I/O failure that appears randomly and inconsistently looks like hardware or filesystem damage. It took ruling out actual corruption first, then tracing back through what was loading when, before the sequencing issue became visible.

VMD (Volume Management Device) is an Intel storage controller architecture used in modern NVMe configurations. When the kernel module for it loads late or out of order, the SSD can appear absent during early boot. The symptom is indistinguishable from a dead drive unless you know to look at the module load sequence.

Resolution

Fixed by reordering boot-time kernel modules in the init configuration to ensure the VMD controller driver loaded before the storage access sequence began. Rebuilt manually, confirmed the drive was consistently visible across several reboots, and came back up clean.

Both failures had the same structure. A visible thing breaks. The visible thing is not the broken thing. The broken thing is one layer underneath it, and the error output doesn't tell you that directly.

In the first incident, the display manager crash was real but downstream. In the second, the I/O failure was real but the cause was a sequencing problem, not data corruption. Fixing the thing you can see first is almost always wrong. Getting inside the system and asking what failed before this failed is the actual work.

The chroot workflow is worth knowing well. When a system won't boot, you still need to run commands against it. A live USB plus chroot is how you do that without reinstalling. It's not complicated, but you have to know it exists before you need it.

The VMD issue is also worth filing away. Modern NVMe storage on Intel platforms can behave this way after kernel updates. If a drive seems to disappear intermittently at boot after an update, module load order is worth checking before assuming hardware failure.

ELI5 tldr
01 The front door of a building was stuck. Everyone assumed the door was broken. The lock mechanism behind the wall was broken. The door was just the first thing that fell over when it failed.
02 Went in through the emergency entrance, found the actual broken part, rebuilt it from the inside, and left through the front door like nothing happened.
03 Second time: the computer couldn't reliably find its own drive because two things were trying to start in the wrong order, like a key trying to work a lock that hasn't been installed yet. Fixed the order. Drive stayed visible. Problem gone.
